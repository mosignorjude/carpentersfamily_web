# Design: Event Duration (One Day or Many) and One 12-Hour Clock

- **Date**: 2026-11-04
- **Status**: Approved in chat — awaiting spec review
- **Migration**: `supabase/migrations/20261104120000_event_duration_and_12hour_time.sql`
- **Areas**: event scheduling, event create/edit forms, every surface that renders an event time

---

## 1. Intent and Why

Two separate complaints, one underlying cause: an event's schedule is modelled as a single
instant and rendered by whichever `Intl.DateTimeFormat` each component happens to build.

**An event cannot last more than a moment.** `public.events` stores `starts_at timestamptz
not null` and nothing else about length
([20261003101500:5](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql)).
There is no end, no duration, no day count. A convention that runs Friday to Sunday is recorded
as its first minute, and five places then treat that minute as the whole truth:

| site | code | consequence today |
| --- | --- | --- |
| `src/lib/home-dashboard.mjs:215` | `startsAt < nowTimestamp` → `return null` | the row is dropped from the home feed |
| `src/lib/home-dashboard.mjs:455` | `.gte("starts_at", nowIso)` | the "upcoming events" count excludes it |
| `src/lib/home-dashboard.mjs:837` | `.gte("starts_at", nowIso)` | the feed query cannot even see it |
| `src/components/events/events-page-view.tsx:89-106` | `new Date(event.starts_at).getTime() >= now` | it moves from Upcoming to Past |
| `src/components/events/event-card.tsx:78` | `isPastScheduled` | the card greys out and reads as past |

So on the evening of day one, a three-day event vanishes from the home page, its count drops,
and its card says "past" while it is still happening.

**The clock has no house style.** Nine places format an event or meeting time in 24-hour and one
in 12-hour, each independently:

| # | site | decision |
| --- | --- | --- |
| 1 | `src/components/events/event-card.tsx:41-46` | `hour12: false` |
| 2 | `src/app/(member)/events/[eventId]/dashboard/page.tsx:306-311` | `hour12: false` |
| 3 | `src/lib/staff-presentation.mjs:29-34` | `hour12: false`, `en-GB` |
| 4 | `src/app/(member)/officers/members/page.tsx:250-253` | `timeStyle: "short"`, `en-NG` → 24-hour |
| 5 | `src/components/attendance/attendance-hub-view.tsx:73-82` | two `timeStyle: "short"` → 24-hour |
| 6 | `src/components/home/next-up-events-card.tsx:14-20` | `timeStyle: "short"` → 24-hour |
| 7 | `src/lib/email/format-schedule.ts:9-13` | `timeStyle: "short"` → 24-hour |
| 8 | `src/lib/notifications/meaningful-change.ts:44-52` | `hourCycle: "h23"`, with a `slice(11, 19)` fallback at :40 that returns the raw **UTC** clock |
| 9 | `20261027000000…sql:1461` | `to_char(…, 'FMHH24:MI')` in the reminder body |
| — | `src/components/tickets/tickets-storefront-view.tsx:57-62` | `hour12: true` (the only one) |

A member can therefore see `19:00` on the event card, `7:00 PM` on the ticket page and `19:00
WAT` in the email for the same event.

**The entry form is one indivisible box.** Both the create form
([`create-event-disclosure.tsx:163-172`](../../src/components/events/create-event-disclosure.tsx))
and the edit form ([`event-edit-modal.tsx:165`](../../src/components/events/event-edit-modal.tsx))
use a single `<input type="datetime-local" name="starts_at">`. A browser renders that widget in
24-hour form for a Lagos or en-GB locale, so the requirement "written as AM or PM" cannot be met
by that input at all — there is no attribute that forces 12-hour entry.

## 2. Goals, Non-Goals, Anti-Goals

### Goals

- An event can be recorded as lasting **1 to 30 days**, entered as a number of days.
- The day count decides whether the event is still live, so a multi-day event stays in the home
  feed, in the count, in Upcoming, and in live card styling until the end of its last day.
- Event times are entered as **separate date and time controls**, and the time control cannot
  accept a 24-hour value.
- One 12-hour clock everywhere an event time appears — app, staff views, emails and the
  database-generated reminder text.
- Existing events keep today's behaviour with no data migration: every one of them is one day.

### Non-Goals

- Per-day sessions, a different start time on each day, or an uneven end time
  (Friday 7:00 PM → Sunday 2:00 PM). The model is a start instant plus a whole number of days.
- Changing reminder slots, attendance lateness cutoffs, the ticket sales window or any finance
  guard. They keep keying off `starts_at`, deliberately.
- A timezone picker. `events.timezone` stays at its `Africa/Lagos` default and is still not
  exposed by the form.
- Renaming `starts_at` or moving to a `date` + `time` pair.

### Anti-Goals

- **No second source of truth for "when does an event end" that can drift from `duration_days`.**
  `ends_at` is generated by the database and cannot be written by anyone.
- **No per-component `Intl` formatter for event time after this ships.** Any new surface calls
  the shared helper, so the ninth 24-hour decision cannot reappear.
- **No silent acceptance of the old combined `starts_at` field.** The action allowlist stops
  accepting it, so a stale client is rejected rather than quietly trusted.

## 3. The Rules

### 3.1 Duration

`duration_days` is an integer, `1 <= duration_days <= 30`, `not null default 1`. It is the
number of calendar days the event occupies, inclusive of the day it starts. One day is today's
behaviour and is the value of every existing row.

### 3.2 The live window

The event is live from `starts_at` until the same wall-clock time `(duration_days - 1)` days
later — a 3-day event starting Friday 7:00 PM is live until Sunday 7:00 PM, not until Sunday
midnight. For a 1-day event the window closes at its own start, which is today's behaviour:

```
ends_at = starts_at + ((duration_days - 1) * interval '24 hours')
```

Africa/Lagos has observed no DST since 1977, so 24-hour steps equal calendar-day steps for every
date this club can schedule inside the `1900–2200` range enforced by
`events_starts_at_range_check` ([`20261003102500`](../../supabase/migrations/20261003102500_event_date_range_validation.sql)).
That also makes the expression immutable, which is what allows `ends_at` to be a generated column.

`isEventLiveOrUpcoming(event, now)` is `event.ends_at > now`. One rule, used by all five sites in
§1. `starts_at` remains the sort key so ordering does not change.

### 3.3 The clock

One formatter renders event and meeting times: `7:00 PM`, `12:05 AM`, `12:00 PM`. Noon is
`12:00 PM` and midnight is `12:00 AM`. The hour is shown without a leading zero; minutes keep two
digits. Minutes are entered in 5-minute steps (`00, 05, … 55`) — a 12 × 60 select is unusable and
club events start on round times.

### 3.4 Deliberately unchanged

| behaviour | why it stays on `starts_at` |
| --- | --- |
| Reminder slots `7d/3d/24h/2h before` and the `starts_at <= p_now` skip ([:1429](../../supabase/migrations/20261027000000_scalable_notification_outbox_and_reminders.sql)) | a reminder is about the start, not the end |
| Attendance late cutoff `starts_at + cutoff_minutes` ([:573](../../supabase/migrations/20261003103000_meetings_minutes_attendance.sql)) | lateness is measured against the announced start |
| Ledger posting and the archive retention boundary (`target.starts_at < statement_timestamp()`) | finance timing is outside this feature's scope |
| The `event_details_updated` audit shape | gains `duration_days`, but its meaning is unchanged |

## 4. Architecture

### 4.1 Schema

One migration, `20261104120000_event_duration_and_12hour_time.sql`:

```sql
alter table public.events
  add column duration_days integer not null default 1,
  add constraint events_duration_days_check check (
    duration_days between 1 and 30
  );

-- Separate statement: ends_at references duration_days, and a generated column may not
-- depend on a column introduced by the same ALTER command list.
alter table public.events
  add column ends_at timestamptz generated always as (
    starts_at + ((duration_days - 1) * interval '24 hours')
  ) stored;

comment on column public.events.duration_days is
  'Inclusive calendar days the event occupies. 1 = single day. Drives ends_at.';
comment on column public.events.ends_at is
  'Generated end of the live window. Never written directly.';

-- events grants SELECT per column; an ungranted column breaks reads silently.
grant select (duration_days), select (ends_at) on public.events to authenticated;
```

The grant is load-bearing twice over: output columns **and** filter/order columns are checked
against column privileges, which is exactly why the earlier `timezone` column needed
[`20261027140610`](../../supabase/migrations/20261027140610_grant_events_timezone_to_authenticated.sql).
`ends_at` is filtered by the home feed, so a missing grant empties that query rather than erroring
visibly.

**Fallback.** If the local stack refuses the generated column, `ends_at` becomes a plain column
maintained by `private.guard_event_write()`; every other part of this design is unaffected because
all consumers go through `isEventLiveOrUpcoming` / `ends_at`.

### 4.2 RPC contract

Four functions gain one parameter, `p_duration_days integer`, appended last:

| function | current arity | source |
| --- | --- | --- |
| `private.create_event` | 11 args | current body at [`20261013040328:30`](../../supabase/migrations/20261013040328_event_finance_workspace_slk_behaviour.sql) |
| `public.create_event` | 11 args | [`20261003101500:1108`](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql) |
| `private.update_event_details` | 6 args | [`:578`](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql) |
| `public.update_event_details` | 6 args | [`:1133`](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql) |

**The old signatures are dropped before the new ones are created.** With both arities present, a
PostgREST call that names only the eleven old parameters resolves to the old function and the day
count is discarded without an error. The migration therefore runs, in order:

1. `drop function public.create_event(text, text, timestamptz, text, text, boolean, boolean, boolean, boolean, boolean, boolean)` and the matching `private.` one;
2. `drop function … update_event_details(uuid, text, timestamptz, text, text, text)` for both schemas;
3. recreate all four with `p_duration_days integer` last;
4. re-issue `revoke … from public, anon, service_role` and `grant execute … to authenticated` against the **new** type lists, matching the existing block at [:1223-1246](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql).

Inside the functions:

- validation joins the existing `23514` chain: `p_duration_days is null or p_duration_days not between 1 and 30`.
- `private.create_event` adds `duration_days` to its `insert … values`.
- `private.update_event_details` adds `p_duration_days` to the **no-op early return** at [:634-639](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql), to the `update … set` list at :641-645, and to both `jsonb_build_object` calls in the `event_details_updated` audit row at :651-658. Omitting it from the early return is the trap: an edit that changes **only** the day count would `return` having written nothing, report success, and leave the audit trail empty.
- `guard_event_write()` adds `or new.duration_days is distinct from old.duration_days` to the edit-authorization branch at [:326-329](../../supabase/migrations/20261003101500_events_roles_budgets_lifecycle.sql). The RPC already enforces role and `status = 'scheduled'`, so this is defence in depth behind `security definer`.

### 4.3 `src/lib/event-schedule.mjs` (new)

All schedule meaning lives here, so the app has exactly one clock and one length rule. Pure,
importable, no React, no Supabase — this is the unit the tests aim at.

| export | contract |
| --- | --- |
| `parseEventSchedule(input)` | `{eventDate, startHour, startMinute, meridiem}` → `{ok: true, startsAt}` or `{ok: false, field, message}`. Validates `YYYY-MM-DD` as a real date, hour `1–12`, minute in `MINUTE_STEPS`, `meridiem` in `AM`/`PM`; maps `12 AM`→`00`, `12 PM`→`12`; returns the same Africa/Lagos `+01:00`-derived UTC ISO that `eventDateTimeToISOString` produces today. |
| `splitInstantForForm(startsAtIso)` | instant → `{eventDate, startHour, startMinute, meridiem}` in Lagos wall-clock terms. Replaces the `+1h` hack at [`event-edit-modal.tsx:16-19`](../../src/components/events/event-edit-modal.tsx). |
| `MINUTE_STEPS` | `[0, 5, 10, … 55]`, the shared minute grid for form and validator. |
| `formatEventTime(value)` | `7:00 PM` / `12:05 AM`. The only event-time formatter. |
| `formatEventDateSpan(startsAtIso, durationDays)` | `6 Nov 2026` for one day, `6–8 Nov 2026` for three. |
| `formatEventDurationLabel(durationDays)` | `1 day` / `3 days`. |
| `isEventLiveOrUpcoming(event, now)` | `event.ends_at > now`, with the same defensive shape checks the home feed already applies to rows. |
| `eventLiveWindowLowerBound(nowIso, maxDays)` | the widened `starts_at` lower bound for queries (§4.5), `maxDays` defaulting to `MAX_DURATION_DAYS`. |

`MAX_DURATION_DAYS = 30`, matching the database check. `eventDateTimeToISOString`
([`event-validation.mjs:25`](../../src/lib/event-validation.mjs)) is **kept unchanged** —
announcements still use it for `expires_at` ([`actions.ts:3278`](../../src/app/actions.ts)).

### 4.4 The set-event and edit forms

`Date & Time` becomes three groups of controls, in both
[`create-event-disclosure.tsx:154-173`](../../src/components/events/create-event-disclosure.tsx)
and [`event-edit-modal.tsx:160-175`](../../src/components/events/event-edit-modal.tsx):

| label | control | name |
| --- | --- | --- |
| Date | `<input type="date">` | `event_date` |
| Time | three selects: hour `1–12`, minute `MINUTE_STEPS`, `AM`/`PM` | `start_hour`, `start_minute`, `meridiem` |
| Runs for | select `1 day` … `30 days` | `duration_days` |

Native `type="time"` is rejected on purpose: its widget follows the browser locale, so an en-GB or
Lagos browser shows a 24-hour spinner and "written as AM or PM" becomes unenforceable at the point
of entry. The selects are already the club's idiom elsewhere, so this adds no new visual language.

The edit form pre-fills from `splitInstantForForm(starts_at)` and `duration_days`, so a round trip
through edit cannot shift the stored instant — today that only works because of the hardcoded
`+1h`.

### 4.5 Server actions

### 4.6 The 12-hour sweep

All nine 24-hour sites in §1 call the shared helpers. `tickets-storefront-view.tsx:57-62` already
reads `hour12: true` and is repointed at `formatEventTime` so it cannot drift back. The dashboard
header gets the span (`6–8 Nov 2026`) plus `7:00 PM (3 days)` at
[`event-dashboard-view.tsx:575/585`](../../src/components/events/dashboard/event-dashboard-view.tsx).
The staff audit formatter and the meaningful-change summary keep their own shapes but borrow the
clock; `meaningful-change.ts:40`'s `slice(11, 19)` fallback, which leaks a raw **UTC** time, is
replaced by the helper.

The one SQL piece, the reminder body at [`20261027000000:1459-1464`](../../supabase/migrations/20261027000000_scalable_notification_outbox_and_reminders.sql).
`to_char` prints `am`/`pm` lowercase and `initcap` would destroy `FMMonth`, so the meridiem is
appended by hand:

```sql
v_when_local := pg_catalog.to_char(
  v_event.starts_at at time zone v_timezone,
  'FMDay, FMDD FMMonth YYYY "at" FMHH12:MI '
) || case
    when pg_catalog.extract(hour from
      v_event.starts_at at time zone v_timezone) < 12
    then 'AM' else 'PM'
  end;
```

The assignment sits inside **`public.evaluate_notification_reminders`**, which spans
[:1347-1708](../../supabase/migrations/20261027000000_scalable_notification_outbox_and_reminders.sql)
of the shipped migration — about 360 lines. Changing the clock therefore means re-creating that
whole function in `20261104120000…`, copied verbatim from the shipped file with only the
`v_when_local` expression at :1459-1462 altered. Already-applied migration files are never
rewritten in this repo, so the old definition stays in history and the new one supersedes it.
The plan should treat that copy as its own task with its own review, because a transcription
error in 360 lines of security-definer code is the largest single risk in this design.

## 5. Data Flow

Create:

```
Date + hour + minute + AM/PM + days
  → createEventAction (allowlist, parseEventSchedule, 1..30 guard)
  → rpc create_event(p_…, p_duration_days)
  → private.create_event: role + status + range validation → insert
  → events.starts_at (UTC instant), duration_days = N
  → ends_at generated = starts_at + (N-1)*24h
  → guard_event_write → reminder sync → audit → notifyNewEventScheduled
```

Read:

```
select … starts_at, duration_days, ends_at   (column grants must cover each)
  → isEventLiveOrUpcoming(row, now)          (home feed, count, events page, card)
  → formatEventDateSpan + formatEventTime + formatEventDurationLabel
```

## 6. Failure Modes and Safety

| failure | how it is contained |
| --- | --- |
| `ends_at` column not granted | the home feed returns nothing and `safeQuery` marks the card unavailable, as every other failed home query does. A pgTAP/grant test plus the browser check catches it before merge. |
| Stale client posts `starts_at` | `eventFieldsOnly` rejects → `invalid-request` redirect. No silent fallback. |
| Day-count-only edit | the early-return comparison includes `duration_days`, so the write and the audit row both happen. Proved by a pgTAP test that changes only the count. |
| Old and new RPC arities coexisting | migration drops the old signatures first; a local `db reset` + `db push --local` proves exactly one `create_event` remains per schema. |
| Bad minute/hour from a crafted form | `MINUTE_STEPS` and the `1–12`/`AM`/`PM` checks reject before any RPC; the database independently enforces `1–30`. |
| `12 AM` / `12 PM` mis-mapped | the two boundary cases are named in tests, not reasoned about in prose. |
| Generated column refused by the stack | documented fallback (§4.1); consumers are unaffected because they read `ends_at` either way. |
| Editing a completed event's length | already impossible: `private.update_event_details` refuses anything not `scheduled` and unarchived (:631-633). |
| Existing events | default to `duration_days = 1`, so `ends_at = starts_at` and behaviour is byte-identical to today. |

Deployment order follows the standing ruling for this project: the migration is applied to
production **before** the branch is merged, and the apply itself is operator-gated — I do not run
`supabase db push` without `--local`.

## 7. Testing

TDD throughout: each behaviour below is written, run, and **seen to fail** before production code.

**`tests/event-schedule.test.mjs`** (new, pure):

- `parseEventSchedule` accepts `2026-11-06`, `7`, `30`, `PM` → the same ISO `eventDateTimeToISOString("2026-11-06T19:30")` returns today.
- `12 AM` → hour `00`; `12 PM` → hour `12`; `1 AM` → `01`.
- Rejects: impossible date (`2026-02-30`), hour `0` and `13`, minute `7` (off grid), meridiem `pm`
  lower-case and empty, missing field, non-string.
- `splitInstantForForm(parseEventSchedule(x)) === x` for a swept set of instants — the round trip
  the edit modal depends on.
- `formatEventTime` → `7:00 PM`, `12:05 AM`, `12:00 PM`; always Lagos regardless of host timezone.
- `formatEventDateSpan` one day vs three days vs crossing a month end.
- `isEventLiveOrUpcoming`: day 2 of 3 is live; a 1-day event one second past start is not; a
  3-day event one second past `ends_at` is not.
- `eventLiveWindowLowerBound` never reaches back further than `MAX_DURATION_DAYS - 1` days.

**Existing app tests that must change:**

## 8. Out of Scope

- Per-day sessions or distinct daily start times.
- Making reminders, attendance cutoffs or ticket windows duration-aware.
- A timezone picker, or fixing `events.timezone` being unsettable from the form.
- Making the notification "what changed" summary mention a day-count change specifically.
- Announcements' `expires_at`, dues dates and finance dates — they keep `type="date"` / 24-hour as
  they are, because they are not event times.
- Backfilling anything.
