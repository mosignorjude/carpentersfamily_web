# Approval-gated development and security roadmap

Each step is a separate approval gate. Before a step, explain its functional scope, assets, actors, threats, boundaries, controls, and tests. After implementation, run the approved verification, report failures/findings, explain the next step, and stop for approval. Feature completion requires both an authorized-path test and explicit forbidden-path tests. Do not implement future steps under an earlier approval.

## Steps

### 4. Dues and dues privacy — Implemented and locally verified

- **Objective/dependencies:** Monthly obligations, rate history, payments, write-offs, corrections and private dues report; depends on Steps 2–3 and resolved D-007.
- **Assets/threats/boundary:** Individual dues and payment history; forged identity/month/amount, duplicates/overlap, unauthorized write-off, concurrency, stale sessions and historical alteration across Browser → Next.js → PostgreSQL.
- **Auth/access/database:** Members see their own dues and payment history; active members see only the club-wide aggregate. Active Executive/Admin/Backup Admin can review individual dues and record payments/write-offs. Only Admin/Backup Admin can correct payments or change a scheduled rate. Forced RLS is on every dues table; browser roles are not authoritative.
- **Validation/exposure/audit:** PostgreSQL checks full-month coverage, applicable historical rates, exact whole-Naira totals, dates, membership periods and required reasons. Payment, write-off, correction and rate changes are atomic and audited. Current-month final disposition is unique; previous corrections remain immutable.
- **Resolved D-007 behavior:** Approval/reactivation month is included; deactivation month is excluded. Inactive gaps are not billed. Members may prepay selected full months at applicable rates. Rates take effect next month; a scheduled future rate may be corrected before it takes effect, while already-paid month snapshots remain unchanged. Write-offs apply only to old unpaid months.
- **Implementation:** Added the dues schema, status-view, future-rate correction and audit-pagination index migrations, server-validated actions, the dues page/forms, and the dues privacy regression suite. Payment and officer audit history use bounded 50-row pages with navigation; rate history is bounded to the 1,200-month application horizon.
- **Step 4 verification:** All three local database suites pass (135 pgTAP assertions). They cover self-only reads, no IDOR, denied member mutations, Executive/Backup/Admin boundaries, future prepayment, exact totals, duplicate/overlap rejection, write-off boundaries, deactivation/reactivation, payment/rate correction audit, historical retention, stale sessions and aggregate-only exposure. `npm run lint` and `npm run build` pass.
- **Limits/findings:** Each payment/write-off/correction accepts up to 1,200 months (100 years) to bound request and database work. Rate history is capped at 1,200 configured rows, matching that horizon. There is no app-level per-actor/IP time-window limiter for dues RPCs; active-role checks, unique month dispositions, exact rate totals and the per-call batch cap constrain each call, but do not throttle repeated authorized calls. Thresholds were not invented because an overly low limit could block legitimate bulk bookkeeping. Review platform limits and any desired database throttle in deployment/maintenance. Google OAuth remains unverified until provider credentials are configured.

### 6. Receipt storage

- **Objective/dependencies:** Optional receipts in private Supabase Storage; depends on data ownership model and Steps 4–5.
- **Assets/threats/boundary:** Receipt bytes and links; malicious file, path traversal, guessed ID, public exposure across browser/Storage boundary.
- **Auth/access/database:** Private bucket. Active members may download receipts linked to shared club/event financial records they can read; uploads require an authorized transaction officer. Any personal dues receipt must follow the existing owner/officer dues privacy rules. Object ID alone grants no access.
- **Validation/exposure/audit:** Size and content/type allowlist, generated safe filename, no executable/active content where inappropriate; avoid logging URLs/content.
- **Tests/failure:** Type spoof, oversize, unauthorized cross-record download, path tricks. Reject unsafe content and fail closed on storage errors.
- **Step 6 implementation:** Added a private `club-finance-receipts` bucket and forced-RLS receipt metadata table. Authenticated browser roles have restrictive deny policies for direct Storage reads/writes; server-only routes perform bounded file transfer using the Supabase secret key. The upload route requires same-origin POST, active officer role, an unvoided shared finance record, exact multipart fields, a generated object key, matching allowlisted extension/MIME/magic bytes, and a 4 MiB limit. Database procedures reserve and finalize an uploader-owned receipt, confirm the Storage object exists, preserve a checksum, and append a minimized audit row. Active members can read available receipt names and download through an authorization-checked attachment route. Dues receipts and event receipts are not included.
- **Step 6 verification:** The migration applied to local Supabase. All five database suites pass **207 pgTAP assertions**, including active-member metadata visibility, pending/inactive denial, direct table write denial, Executive/Admin/Backup Admin upload reservations, invalid MIME/size/path rejection, unknown transaction rejection, private-bucket constraints, and audit-schema configuration. Six Node regression tests pass for PDF/JPEG/PNG signatures, MIME/extension spoofing, oversized/empty files, path traversal, safe filenames, bounded streamed form parsing, and missing `Content-Length`. `npm run lint` and `npm run build` pass. Local HTTP checks returned 404 for an unauthenticated receipt request and redirected a cross-origin upload to a denied notice. A successful authenticated byte-upload/download was not exercised end-to-end; hosted Storage/Vercel behavior remains unverified.
- **Step 6 finding — Low, non-blocking:** There is no per-user or per-IP upload rate limiter. A compromised or misused finance-officer account can repeatedly upload valid files and consume Supabase Free storage/egress. Current controls limit each file to 4 MiB, limit one pending upload per actor, require an active officer, and fail closed on quota errors. Add an explicit lifetime or time-window threshold if the club wants one; thresholds were not invented because legitimate receipt volume is not yet known.
- **Step 6 finding — Low, non-blocking:** Byte signatures confirm the declared PDF/JPEG/PNG format but do not detect malware or every malformed/polyglot document. The app serves receipts only as forced downloads and never interprets them as HTML; members still need to use normal endpoint protection when opening downloaded files. File scanning or quarantine can be considered if the club adopts an appropriate service/operations budget.
- **Free-tier boundary:** The 4 MiB cap fits below Vercel Functions' 4.5 MB request/response payload limit. Supabase Free still has finite storage and bandwidth quotas; this implementation adds no paid storage or upload service.
